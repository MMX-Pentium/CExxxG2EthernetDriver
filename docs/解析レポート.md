# CE100G2.raw 解析レポート

## 結論

CE100G2 の LAN 8 ポートは、Intel Atom C3000 内蔵 X553 の 2 機能に接続された
Marvell 88E6190 L2 スイッチ配下にあります。Ubuntu で不足しているのは X553 自体の
ドライバではなく、基板上の 88E6190 と CPU ポートの配線を Linux に伝える部分です。

このため、Ubuntu の `mv88e6xxx` と DSA を利用し、基板情報を登録するモジュールと、
X553 PCS を2.5Gbpsへ初期化するパッチ済み `ixgbe` をDKMS化しました。3.10 用の
製品 OS モジュールは ABI が異なるため、Ubuntu へ直接コピーしていません。

## ダンプから確認した構成

- 製品 OS: CentOS/RHEL 7 系、カーネル
  `3.10.0-514.OpenVA.5.6.1019.el7.x86_64`
- DMI 製品名: `NCA-2011Z-TM2J`
- 独立 NIC: Intel I211 (`8086:1539`) 2 ポート
- スイッチ CPU 側: Intel X553 Backplane (`8086:15c2`) 2 機能
- L2 スイッチ: Marvell 88E6190
- 製品 OS のユーザーポート: `eth1` ～ `eth8`
- 製品 OS の CPU 側ポート: `inner0`、`inner1`

製品 OS には `dsa-drv.ko`、`mv88e6190-drv.ko`、カスタム `ixgbe.ko`、および
基板コールバック用 `aewin.ko` が含まれていました。起動スクリプトは `inner0` と
`inner1` を起動し、GRO/GSO を無効化してからスイッチモジュールをロードしています。

旧 DSA モジュールの解析では、スイッチポート 1～8 がユーザーポート、9 と 10 が
CPU ポート、0 は未使用でした。この配線を `dsa_mv88e6xxx_pdata` として登録します。

## Ubuntu 側の実装

Ubuntu 24.04 の `ixgbe` は X553 用 MDIO バスを `ixgbe-mdio-<PCIアドレス>` として
公開します。`ce100g2_switch` は次の順に動作します。

1. 対応する Lanner DMI 製品名を確認する
2. PCI ID `8086:15c2` の function 0/1 と各 netdev を取得する
3. function 0 の `ixgbe-mdio-*` バスを取得する
4. 88E6190 のポート 1～8、CPU ポート 9/10 を登録する
5. 標準 `mv88e6xxx` DSA ドライバへバインドする
6. CPU ポート 9/10 の CMODE を 2500BASE-X に設定し、2.5Gbps・全二重・
   link-up を固定する
7. 対応DMI上では、X553 PMD Flex Mask の速度を2.5Gbpsへ設定して内部PCSを再起動する
8. Atom C3000のI801 SMBus上にあるバイパス制御MCUを通常NICモードへ設定する

`ixgbe` の初期化順序に依存しないよう、モジュールは最大 60 秒間、2 秒間隔で登録を
再試行します。systemd サービスは X553 親ポートを UP にし、製品 OS と同様に
GRO/GSO を無効化します。また、2つの外部I211もUPにして管理/WANのPHYを起動します。

## ビルド検証

- Ubuntu noble-updates の公式 `linux-headers-6.8.0-138-generic`
- GCC 13.3
- Kbuild の MODPOST と最終リンクまで成功
- 生成モジュールの vermagic:
  `6.8.0-138-generic SMP preempt mod_unload modversions`
- Debian バイナリパッケージの生成と内容検査に成功
- パッチ済み `ixgbe.ko` と `ce100g2_switch.ko` の同時ビルド、MODPOST、最終リンクに成功

## 実機確認状況

NCA-2011Z-TM3J、Ubuntu カーネル 6.8.0-100-generic では、88E6190 の検出、
PHY 1～8 の登録、`lan1`～`lan8` の生成、および DSA tree の setup まで確認済みです。

0.1.3 では CPU ポートの MAC Control を 2500Mbps・全二重・link-up に設定しても、
X553 親インターフェースが `NO-CARRIER` のままでした。解析の結果、legacy DSA
platform data には `phy-mode` を指定する手段がなく、88E6190 CPU ポートの CMODE
設定が呼ばれないことが分かりました。0.1.4 では上流
`mv88e6390_port_set_cmode()` と同じ Port Status の CMODE 値 `0x0b` を明示します。

0.1.4の実機ログでは両CPUポートのPort Statusが設定前から `0x230b` であり、CMODEは
既に2500BASE-Xでした。それでもX553はリンクアップしませんでした。採取した
`ethtool -d` のレジスタダンプでは、両X553の `IXGBE_LINKS` が `0x20000008` でした。
`LINKS_UP` は立っておらず、速度フィールドは1Gbpsを示します。すなわちスイッチ側
ではなく、X553内部PCSが1Gbpsのままなのが直接の不一致です。

製品 OS の追加 `ixgbe.ko` は Intel ixgbe 5.3.7 でした。2.5Gbps backplane の場合、
この版もLinux 6.8と同様にX553 PCS設定をNVM/ファームへ任せる実装でした。一方、
Ubuntuの `ixgbe_setup_kr_x550em()` も2.5Gbpsでは設定を変更せず復帰します。0.1.5は
Ubuntu `6.8.0-100.100` の公式ixgbeソースを基に、この分岐だけを対応Lanner DMIへ
限定して修正します。PMD Flex MaskのAN/SGMIIを解除し、速度値を2.5Gbpsへ設定して
内部PHYの再起動を要求します。他機種では元の処理を維持します。

0.1.5の実機試験では、標準の非SFPリンク設定がNBASE-T互換性対策として2.5Gbpsを
候補から除外するため、上記KR処理へ到達しないことが判明しました。0.1.6では対応DMI
だけ2.5Gbpsを保持します。また、起動時に2つのX553機能が共有NVMを同時に検証すると
function 0だけ一時的なチェックサムエラーになる事象があり、200ms間隔で最大5回の
再試行を追加しました。手動再bindでは同じNVMの検証に成功しており、恒久的なNVM
破損ではありません。

0.1.6では両functionの安定したプローブとDSA初期化に成功しましたが、PCS設定ログは
出ませんでした。PHY種別は `ixgbe_phy_x550em_kr` である一方、リセット後の
`autoneg_advertised` に1Gbps値が残り、能力選択が再実行されていませんでした。
0.1.7では対応DMIかつPCI ID `8086:15c2` の非SFPリンク設定要求を固定2.5Gbpsへ
上書きし、KR/PCS処理を必ず呼び出します。

0.1.7の実機試験では、DKMS版をルートファイルシステムへ配置しただけではinitramfsの
標準`ixgbe`が先にロードされることも判明しました。initramfs内の`modules.dep`は
`kernel/drivers/.../ixgbe.ko.zst`を明示しており、単純な`update-initramfs`でも標準版を
保持していました。0.1.8では専用initramfs-toolsフックから`manual_add_modules ixgbe`を
実行し、`updates/dkms/ixgbe.ko.zst`を収録・優先させます。アンインストール後は
initramfsを再生成してUbuntu標準版へ戻します。

この構成でロード中の版が`6.8.0-100-ce100g2-0.1.7`となること、両X553でPMD Flex Maskが
`0x48000000`から`0x70000000`へ更新されること、`ethtool`が両方とも2500Mb/s・full duplex・
link detected yesを返すことを実機確認しました。

0.1.8導入後の外部ポート試験では、筐体刻印LAN2がLinuxの`lan2`に一致しました。
`lan2`は1000Mb/s・full duplexでリンクし、systemd-networkdがDHCPから
`192.168.100.2/24`を取得しました。DHCPゲートウェイ`192.168.100.1`へのICMPは4送信・
4受信・損失0%、インターフェース統計もRX/TXエラーとドロップが0でした。外部IPへの
ICMPは試験用ルーター側で到達できませんでしたが、L2転送、外部PHY、DHCP、同一LAN内の
パケット疎通は正常です。

筐体LAN1～LAN7は、ケーブルを順に接続した実機試験でLinuxの`lan1`～`lan7`と刻印が
一致し、リンクアップすることを確認しました。LAN8だけはケーブル挿入時に一瞬
1000Mb/sを検出した後でリンクダウンし、筐体WANへ同じケーブルを挿すとLinuxの
`lan8`が継続リンクする状態でした。LAN8の強調刻印と製品OSの`aewin.ko`を解析した
結果、この2端子が停電時fail-open用のハードウェア・バイパス対であると判明しました。

製品OSの通常NICモードは、Atom C3000 I801 SMBus（7-bitアドレス`0x37`）へ
コマンド`0x51=0x00`、`0x10=0x03`を書きます。0.1.9は同じ操作をカーネルI2C APIで
実装します。適用2秒後に筐体LAN8がLinuxの`lan8`として1000Mb/s/full duplexで
安定リンクし、DHCP`192.168.100.2/24`取得、ゲートウェイへの4/4応答、FCS/RX/TX
エラー0を確認しました。`0x10=0x03`により電源断時バイパスは維持されます。

同じ試験ケーブルを筐体WANへ移すと、LAN8はリンクダウンし、2個目のIntel I211
`enp6s0`が1000Mb/s/full duplexでリンクアップしました。DHCPから
`192.168.100.3/24`を取得し、ゲートウェイ`192.168.100.1`へ4送信・4受信・損失0%、
CRC、carrier、RX/TX各エラー0を確認しました。これにより通常NICモードでLAN8とWANが
別々のNICへ正しく分離されることを確認しました。

別個体のNCA-2011Z-TM2Jでは、0.1.9でDSAと`lan1`～`lan8`の登録は成功する一方、
両X553親ポートが`NO-CARRIER`となり、全LANポートがリンクしませんでした。製品OSの
`mv88e6190-drv.ko`を解析すると、CPUマスター起動時にポート9/10の内部PHYについて
MMD 4レジスタ`0xa003`を検査し、期待値`0xac20`でない場合にMMD 4レジスタ`0x2000`へ
`0x8140`を書いてPCSを再起動していました。

当該個体の実測値は両ポートともcontrol=`0x0940`、status=`0xa800`でした。製品OSと
同じ再起動を行うと、両X553は直ちに2500Mb/s・full duplexでリンクし、接続中だった
筐体LAN3も1000Mb/s・full duplexでリンクしました。0.1.10ではこの検査と条件付き
再起動をボードグルーへ統合し、DSA生成後に`lan1`～`lan8`を管理上UPにします。

診断時にはDSA初期化中の `mv88e6xxx_irq_poll` が122秒以上待つhung-task警告も一度
記録されました。初期化自体はその後完了しているためPCS不一致とは分離して扱いますが、
起動時間とポーリングIRQ処理は引き続き観察対象です。

## 既知の制約と実機確認項目

- X553と88E6190 CPUポート間の2.5Gbpsリンクアップは実機確認済みです。
- CPU側PHYが未初期化だったNCA-2011Z-TM2Jでも、条件付き再起動による復旧を確認済みです。
- 筐体LAN1～LAN8の印字対応とリンクは実機確認済みです。LAN2/LAN8ではDHCPと
  パケット疎通も確認済みです。
- パッケージは `ixgbe` をDKMSで置換するため、導入・削除後には再起動が必要です。
- 標準 DSA は複数 CPU ポートを認識しますが、製品 OS 固有のポート別 CPU 分散と
  完全に同一とは限りません。初版では全 LAN ポートの疎通を優先しています。
- 6.8 以外の Ubuntu HWE カーネルは DKMS でビルドされますが、現時点では未検証です。
- Secure Boot が有効な場合、DKMS モジュールへの MOK 署名・登録が必要になることが
  あります。
- WANは2個目のIntel I211で、リンクとDHCP疎通を実機確認済みです。恒久的な
  ネットワーク設定は利用環境に合わせて別途行ってください。

実機試験では、まず `ce100g2-switch-status` の結果を保存し、各ポートについて
リンク、DHCP/固定 IP 疎通、再起動後の再現性を確認してください。
